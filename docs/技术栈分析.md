# 技术栈分析

> 本文档对 Task 项目重构的技术选型进行分析，基于"docs/架构说明.md"中所述需求与约束，以及后续架构澄清。

## 一、架构澄清摘要

影响技术选型的关键架构决策：

| # | 决策 | 影响 |
|---|------|------|
| 1 | 记录类型可扩展，不预定义枚举 | 核心层不能硬编码类型列表，需字符串+注册机制 |
| 2 | 每个 Tasker 一个文件夹，内部多个 JSON 分段存储（按数量，不按时间） | 存储层需要分段读写，按文件名排序定段 |
| 3 | core 只有抽象基类，default/timer/account 均为扩展模块 | 框架与内置扩展彻底分离 |
| 4 | 图表/3D 通过启动外部浏览器查看 | 两个技术栈都可通过本地 HTTP + ECharts GL 实现，此维度不再区分优劣 |
| 5 | 图表允许额外启动开销，但不能反复重启 | HTTP 服务保持活跃直到用户关闭图表视图 |
| 6 | 依赖项通过 requirements.txt 安装即视为可接受 | Python 库体积不作为减分项；Java 通过 Gradle 自动下载 .jar 同理 |
| 7 | 启动时只读 taskers.json，不读全部 JSON | 存储层需维护轻量索引 |
| 8 | 3D 柱状图（7列一行，按月分隔）是核心需求 | ECharts GL bar3D 在两个方案中均可使用 |

## 二、候选方案

| 方案 | 语言 | GUI 框架 | 图表/3D 方案 | 图表数据通道 |
|------|------|----------|-------------|-------------|
| **PySide** | Python | PySide6 (Qt) | 外部浏览器 + ECharts / ECharts GL | 本地 HTTP API（Python 内置 http.server 或 aiohttp） |
| **JavaFX** | Java | JavaFX | 外部浏览器 + ECharts / ECharts GL | 本地 HTTP API（JDK 内置 HttpServer 或嵌入式 Jetty） |

不再考虑纯 Web（FastAPI + browser）方案——系统托盘、全局热键等桌面功能无法实现。

## 三、关键维度分析

### 3.1 图表方案（外部浏览器模式）

两个方案在此维度能力完全相同：

- 软件启动本地 HTTP 服务，提供数据查询 API（如 `/api/analysis/attr_count?tasker_id=xxx`）
- `GET /api/chart/3d_monthly?year=2024&month=6` 返回 ECharts GL bar3D 所需的数据集
- 浏览器页面通过 `fetch()` 按需请求数据——用户在浏览器中翻月份时增量加载，无需一次传输多年数据
- Python 用 `webbrowser.open(url)` 启动浏览器；Java 用 `Desktop.getDesktop().browse(uri)`
- HTTP 服务仅在有图表视图时运行，关闭浏览器后软件可手动或超时自动停止服务端口

**图表维度结论：平手。** ECharts GL 的 3D 能力在两个方案中均可使用，通过本地 HTTP API 交互数据。

### 3.2 GUI 框架成熟度

| 维度 | PySide6 | JavaFX |
|------|---------|--------|
| 系统托盘 | QSystemTrayIcon（内置） | java.awt.SystemTray（JDK 内置） |
| 全局热键 | keyboard 库或 pynput（pip） | JNativeHook（.jar + 原生库） |
| 表格视图 | QTableView（Model/View 分离） | TableView（MV 分离） |
| 对话框 | QDialog（内置） | Dialog（内置） |
| 快捷键标注 | QAction.setShortcut（内置） | 需手动管理 KeyCombination |
| 主题 | QSS 样式表（类似 CSS） | JavaFX CSS |
| 浏览器启动 | `webbrowser.open()`（标准库） | `Desktop.browse()`（JDK 内置） |
| HTTP 服务 | `http.server`（标准库）或 aiohttp | `HttpServer`（JDK 内置）或 Jetty |

两者在常规 GUI 功能上相当。Python 的全局热键方案（pynput）比 Java 的 JNativeHook（JNI 原生库）更轻量且无平台兼容性风险。

### 3.3 打包部署

| 维度 | PySide6 | JavaFX |
|------|---------|--------|
| 打包工具 | PyInstaller / Nuitka | jlink + jpackage |
| 典型体积 | 60-100MB（含 Python + Qt，无 WebEngine） | 40-60MB（含裁剪 JRE + JavaFX） |
| 启动速度 | 2-5 秒 | 1-3 秒 |
| 包管理器 | pip + requirements.txt | Gradle |
| 依赖声明 | requirements.txt | build.gradle |

取消 WebEngine 后 PySide6 包体积缩小约 20-30MB（去除了 Chromium 嵌入运行时）。Java 仍有约 20-40MB 的体积优势，但鉴于常驻后台仅启动一次，差异非关键因素。

### 3.4 语言特性权衡

| 维度 | Python | Java |
|------|--------|------|
| 开发速度 | 代码量约少 30-50%，语法简洁 | 代码量较大，样板代码多 |
| Agent 自动化 | 更适合（简洁语法 + 动态特性） | 类型系统复杂，Agent 生成的代码可能需更多修正 |
| 类型安全 | 弱类型，编译期不报类型错误；可通过 mypy 可选静态检查弥补 | 编译期类型检查，类型错误不会进入运行时 |
| 性能 | 解释执行，纯 Python 慢于 JVM JIT | JIT 编译，计算密集型快 |
| 数据迁移 | 直接读取旧 pkl 文件（一次性优势） | 需额外 Python 脚本辅助迁移 |

**Python 弱类型不是致命缺陷：** 项目规模为个人单机工具，类型错误通常在开发测试中就能发现。数据迁移是一次性操作，不是决定性优势。Python 的关键优势在于**代码量更少 + Agent 自动化更高效**——用更少的输入产出更多功能，这才是 Vibe Coding 的核心效率来源。

### 3.5 接口抽象能力

| 模式 | Python | Java |
|------|--------|------|
| 接口定义 | `abc.ABC` + `@abstractmethod` 或 `typing.Protocol` | `interface` |
| 依赖注入 | 构造器注入（鸭子类型） | 构造器注入（接口类型） |
| 门面模式 | 普通类委托 | 接口 + 实现类 |
| 类型安全 | 运行时（mypy 可选静态检查） | 编译期 |

Python 的 ABC 体系足以支撑同构分形架构。差异在于类型检查时机（运行时 vs 编译期）——项目规模下这不是问题。

### 3.6 扩展模块系统

Python 的动态导入 + 注册表模式：

```python
# core/registry.py
class ExtensionRegistry:
    _task_types: dict[str, Type[BaseTask]] = {}
    
    @classmethod
    def register(cls, type_name: str, task_class: Type[BaseTask]):
        cls._types[type_name] = task_class

# extensions/timer/task.py
ExtensionRegistry.register("timer", TimerTask)
```

Java 的 ServiceLoader 或反射方式也能实现，但代码量更大。Python 在此维度有轻微优势。

## 四、最终推荐

### 推荐方案：Python 3.12+ + PySide6 + ECharts（外部浏览器）

**技术构成：**

| 层 | 技术 | 来源 | 说明 |
|----|------|------|------|
| 语言 | Python 3.12+ | 标准 | 类型注解、match/case、pathlib |
| GUI 框架 | PySide6 | `pyside6` (pip) | Qt for Python 官方绑定，LGPL |
| 浏览器启动 | `webbrowser` | 标准库 | 打开系统默认浏览器到本地 HTTP 地址 |
| HTTP 服务 | `http.server` 或 `aiohttp` | 标准库 / pip | 为图表页面提供数据 API |
| 图表 2D | ECharts | CDN（HTML 页面加载） | 饼图、柱状图、折线图、热力图 |
| 图表 3D | ECharts GL | CDN（HTML 页面加载） | 3D 柱状图（bar3D） |
| JSON 存储 | `json` | 标准库 | 分段 JSON 读写 |
| 接口抽象 | `abc.ABC` | 标准库 | 抽象基类（等价 Java interface） |
| 全局热键 | `pynput` | pip | 系统级键盘监听 |
| 剪贴板 | `pyperclip` | pip | 跨平台剪贴板（旧项目已使用） |
| 打包 | PyInstaller | pip | 打包为单个 .exe |
| 测试 | `pytest` | pip | 单元测试框架 |

### 选择理由（按优先级）

1. **代码量更少 + Agent 自动化更高效**：Python 的简洁语法减少约 30-50% 代码量；动态特性使 Agent 生成代码的修正成本更低。这是 Vibe Coding 效率的决定性因素。

2. **扩展模块系统更简洁**：Python 的 `importlib` 动态导入 + 字典注册比 Java ServiceLoader 少约 30% 的样板代码。

3. **接口抽象能力足够**：`abc.ABC` + `typing.Protocol` 提供了与 Java interface 高度同构的抽象能力，同构分形等架构模式可完整迁移。

4. **依赖更轻**：取消 WebEngine 后 PySide6 依赖树更简洁。数据迁移为一次性 Python 脚本可读取旧 pkl（普通优势，非决定因素）。

### 不选 JavaFX 的原因

- 代码量和样板代码多——Agent 自动化生成效率低于 Python
- 弱类型是 Python 的已知 trade-off，在个人项目规模下可接受（mypy 可选弥补）
- 全局热键——JNativeHook（JNI 原生库）比 pynput 有更高的平台兼容性风险

## 五、关键架构决策（与技术栈相关）

### 5.1 图表外部浏览器模式

图表分析通过本地 HTTP 服务 + 外部浏览器实现：

- 用户点击"打开图表"→ 软件启动本地 HTTP 服务（端口可配置，默认 `127.0.0.1:19527`）
- HTTP 服务提供 REST API：`/api/analysis/{analyzer_name}` → 返回 JSON 聚合数据
- 同时 `webbrowser.open("http://127.0.0.1:19527/chart/attr_count.html?tasker_id=xxx")` 打开浏览器
- HTML 页面加载 ECharts/ECharts GL（CDN），初始显示默认时间范围
- 用户在浏览器中切换月份/筛选条件 → JS `fetch()` 请求新的数据 → 图表增量更新
- 用户在软件中点"返回"→ 停止 HTTP 服务 → 释放端口
- 浏览器标签页由用户自行关闭（或软件发送关闭信号）

**为什么不用 QWebEngineView：**
- `pyside6-webengine` 约增加 50MB 打包体积和 Chromium 嵌入运行时
- 外部浏览器方案更简单：软件主窗口只需一个"返回"按钮，浏览器负责全部渲染
- 用户已有一个浏览器运行中（日常使用场景），额外标签页的资源开销远小于嵌入一个独立 Chromium 实例
- 浏览器的开发者工具天然可用——调试 ECharts 图表时可直接 F12

**数据交互设计：**

网页是数据消费者，HTTP 服务是数据提供者。浏览器中的 JS 在用户切换时间范围时发起 `fetch()` 请求，服务端从存储层按需查询并返回 JSON。多年数据不会一次性传输——类似分页，每次请求只返回当前视图所需的数据范围。

### 5.2 JSON 分段存储（按数量）

```
{数据目录}/
├── taskers.json                  # 所有 Tasker 的简要索引
├── {tasker_folder_1}/
│   ├── segment_0001.json        # 第 1-500 条
│   ├── segment_0002.json        # 第 501-1000 条
│   └── ...
└── {tasker_folder_2}/
    ├── segment_0001.json
    └── ...
```

- 不设 index.json——按文件名排序即确定顺序和最新两段
- 默认每段 500 条（可在 settings 中配置）
- Tasker 对象维护 `loaded_segments` 和 `dirty_segments` 追踪脏数据
- 原子写入（先写临时文件再 rename）

### 5.3 扩展模块注册

```python
# core/registry.py —— 唯一的核心注册机制
class ExtensionRegistry:
    _task_types: dict[str, Type[BaseTask]] = {}       # "default" → DefaultTask
    _tasker_types: dict[str, Type[BaseTasker]] = {}   # "default" → DefaultTasker  
    _analyzers: dict[str, Type[BaseAnalyzer]] = {}    # "attr_count" → AttrAnalyzer
    _chart_pages: dict[str, str] = {}                 # "attr_count" → "charts/attr_count.html"
```

扩展模块在 `__init__.py` 中调用 `register()` 完成自注册。core 不导入扩展模块。

## 六、不采用的技术

| 技术 | 原因 |
|------|------|
| JavaFX | 数据迁移需额外 Python 脚本；扩展模块代码量更大；JNativeHook 平台风险 |
| PyQt6 | GPL 协议，PySide6 是 Qt 官方绑定且 LGPL |
| Electron | 包体积 200MB+，内存 300MB+，过度设计 |
| QWebEngineView | 增加 50MB 打包体积和 Chromium 嵌入运行时，外部浏览器方案更轻量 |
| Tkinter | 无现代系统托盘支持，表格视图功能弱 |
| SQLite | 需求明确使用 JSON + OneDrive 同步 |

## 七、与澄清点的逐一校验

| # | 澄清 | 本方案如何满足 |
|---|------|---------------|
| 1 | 类型不预定义枚举 | 字符串注册 + 运行时 hash/get 分发 |
| 2 | Tasker 文件夹 + 分段 JSON | 见 5.2 节 |
| 3 | core 只有抽象 | `BaseTask`/`BaseTasker` 等 ABC，default/timer/account 均为扩展 |
| 4 | Java 经验≠产出效率 | 方案选择不依赖开发者 Java 经验 |
| 5 | 非纯键盘命令系统 | GUI 主交互 + 内联输入框，无独立 command 进程 |
| 6 | 常驻后台，启动开销可忽略 | 打包体积差异非关键 |
| 7 | 图表微服务化 | 见 5.1 节，本地 HTTP 服务 + 外部浏览器 |
| 8 | 依赖通过 requirements.txt 安装 | 所有包在 PyPI 上 |
| 9 | 3D 柱状图（7列一行按月分隔） | ECharts GL bar3D，通过本地 HTTP 提供数据 |

| 11 | Python ABC 等价 interface | 见 3.5 节 |
| 12 | 图表接管主窗口 | 外部浏览器接管可视化职责；软件主窗口显示返回按钮，HTTP 服务按需启停 |
